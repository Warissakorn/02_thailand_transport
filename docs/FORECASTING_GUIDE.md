# แนวทางพยากรณ์จราจรอนาคต + พัฒนาโมเดลพื้นที่ศึกษาจากโมเดลระดับประเทศ

เอกสารแนวทางวิธีการ (methodology guide) สำหรับต่อยอดแบบจำลองนี้ไปสู่งานพยากรณ์ระดับโครงการ:
พยากรณ์จราจร ~30 ปี (รายปี) · ทดสอบโครงการพัฒนา/ขยายถนน/เชื่อมโครงข่าย ·
ดึงโมเดลระดับประเทศไปทำโมเดลพื้นที่ศึกษา (subarea) · ส่งต่อเครื่องมือเฉพาะทาง (PTV Visum + Excel + R)

> สถานะ: **เอกสารแนวทาง — ยังไม่มีการ implement** เขียนตามหลัก NCHRP 765 / TMIP /
> แนวปฏิบัติศึกษาความเหมาะสมโครงการในไทย (สนข./ทล./สศช.) ดูมาตรฐานอ้างอิง §6

## 1. เงื่อนไขก่อนพยากรณ์ — โมเดลฐานต้องผ่านเกณฑ์ก่อน (base-year validation)

หลักสากล: ห้ามใช้โมเดลพยากรณ์อนาคตจนกว่าปีฐานจะผ่านเกณฑ์ validation เพราะความคลาดเคลื่อน
ปีฐานจะ **ทบต้น** เข้าไปในทุกปีพยากรณ์

| เกณฑ์มาตรฐาน (ระดับ link/screenline) | เป้า | โมเดลนี้ (2569, multi-path) |
|---|---|---|
| GEH < 5 ของสถานีนับ | ≥ 85% | **3.1%** ❌ |
| R² จำลอง-vs-นับ | ≥ 0.85 (ระดับโครงการ) | **0.161** ❌ |
| Screenline flow | ± 10% | ยังไม่ได้ทำ screenline |
| Mode share vs สถิติทางการ | ± ไม่กี่จุด | ± 0.5 จุดทุกโหมด ✅ |

**สรุปตรงไปตรงมา:** โมเดลปัจจุบันใช้ได้ระดับ *ยุทธศาสตร์/เปรียบเทียบ corridor* แต่**ยังไม่ผ่านเกณฑ์
ระดับ link** — ก่อนใช้พยากรณ์เพื่อประเมินโครงการจริง ต้องยกระดับตาม [LIMITATIONS.md](LIMITATIONS.md) §6
(สำคัญสุด: พิกัดสถานี AADT จริง + โซนตำบลในเขตเมือง) หรือใช้แนว subarea ใน §4 ของเอกสารนี้
ซึ่งบังคับให้ calibrate ใหม่ในพื้นที่อยู่แล้ว

## 2. พยากรณ์ปีอนาคต ~30 ปี (แบบรายปี)

### 2.1 วิธีหลัก (ถูกหลัก): re-run 4-step ด้วย socioeconomic ปีอนาคต
ตัวขับเคลื่อนอุปสงค์ในโมเดลนี้คือ ประชากรรายโซน (trip gen) + landuse (โรงเรียน/นิคม) —
การพยากรณ์ที่ถูกต้องคือเปลี่ยน **input** เหล่านี้เป็นค่าปีอนาคต แล้วรัน 4 ขั้นใหม่ ไม่ใช่คูณ
growth factor กับ **output**

ข้อมูลปีอนาคตที่ต้องหา (รายโซนหรือรายจังหวัดแล้ว disaggregate):

| ตัวแปร | แหล่ง | ใช้กับ |
|---|---|---|
| การคาดประมาณประชากรรายจังหวัด 2563–2593 | สศช. (NESDC) | trip generation (แทน WorldPop คงที่) |
| GDP/GPP รายจังหวัด + ประมาณการ | สภาพัฒน์/สศช. | trip rate + freight factor (ผูก elasticity) |
| อัตราครอบครองรถ / จดทะเบียนสะสม | กรมการขนส่งทางบก (สถิติรายปี) | สัดส่วนโหมดถนน, trip rate |
| แผนโครงข่าย committed (มอเตอร์เวย์ M6/M81/M82, รถไฟทางคู่/ความเร็วสูง, M-MAP2) | ทล./รฟท./สนข. | future network (§3) |
| แผนพัฒนาพื้นที่ (EEC, เมืองใหม่, นิคมใหม่) | สกพอ./กนอ. | landuse ปีอนาคต |

การปรับพารามิเตอร์: `TRIP_RATE_PAX` และ `FREIGHT_FACTOR` (ใน `config/calibrated_params.py`)
ไม่ควรคงที่ 30 ปี — ผูกกับรายได้/GPP ด้วย elasticity (เช่น trips/คน โต 0.3–0.5 เท่าของ GPP/หัว,
ตันสินค้า โต ~1.0 เท่าของ GDP ภาคผลิต) ประมาณ elasticity จากอนุกรม AADT-vs-GDP ย้อนหลังใน R (§5)

### 2.2 ทำ "รายปี" อย่างถูกวิธี: horizon years + interpolation
**ไม่รันโมเดล 30 ครั้ง** — แนวปฏิบัติมาตรฐาน (ทั้งงานศึกษาไทยและสากล):

1. รันโมเดลเต็มเฉพาะ **ปี horizon เป็นช่วง 5 ปี**: 2569 (ฐาน) · 2574 · 2579 · 2584 · 2589 · 2594 · 2599
2. ปีระหว่างช่วง → **interpolate รายปี** ระหว่างผลปี horizon ด้วย geometric/log-linear:
   `V(t) = V(t0) × (V(t1)/V(t0))^((t−t0)/(t1−t0))`
   ใช้ได้ทั้งระดับ link, OD และตัวชี้วัดรวม (ทำใน Excel/R ได้ทันที)
3. ปีที่มีโครงข่ายเปลี่ยน (เส้นใหม่เปิด) ต้องเป็นปี horizon เสมอ — ห้าม interpolate ข้ามปีเปิดโครงการ
   เพราะ flow กระโดดไม่ต่อเนื่อง (จัดปี horizon ให้ตรงปีเปิดใช้)

### 2.3 วิธีรอง (ยอมรับได้เฉพาะกรณีจำกัด): growth factor / elasticity
- **Growth factor บน OD** (Fratar/Furness): ขยาย OD ปีฐานด้วยอัตราโตรายโซน แล้ว assign ใหม่ —
  ยอมรับได้เมื่อ (ก) horizon ≤ ~5 ปี (ข) โครงข่าย/โครงสร้างพื้นที่ไม่เปลี่ยน (ค) ไม่มี mode shift มีนัย
- **Trend บน link โดยตรง** (แบบ `build_aadt_projection.py` ที่ใช้ project AADT 2566→2569 ในโปรเจกต์นี้):
  เหมาะกับ *ปรับฐานข้อมูลนับ* ระยะสั้นเท่านั้น **ห้ามใช้ยาว 30 ปี** — ไม่สะท้อนความจุอิ่มตัว,
  โครงการใหม่ดึง traffic, โครงสร้างประชากรเปลี่ยน
- ทั้งสองวิธีไม่ตอบคำถาม "โครงการใหม่มีคนใช้เท่าไร" — ต้องใช้ §2.1+§3

### 2.4 ความไม่แน่นอน — ห้ามส่งเลขเดี่ยว
30 ปีมีความไม่แน่นอนสูงมาก แนวปฏิบัติที่ถูกต้อง:
- ทำอย่างน้อย **3 กรณี: สูง/กลาง/ต่ำ** ผูกกับชุดสมมุติฐานที่สอดคล้องภายใน
  (ปชก. สูง+GDP สูง / กลาง / ต่ำ) — ไม่ใช่ ±x% ตามใจ
- รายงานเป็นช่วง (band) ทุกตาราง/กราฟปีอนาคต และ sensitivity ต่อตัวแปรวิกฤต
  (เช่น ค่าผ่านทาง, ราคาน้ำมัน, ปีเปิด committed projects)
- บทเรียนจากข้อมูลจริงของโปรเจกต์นี้: 2563→64 จราจร **−10.2%** (โควิด) แล้ว +7.7%, +4.5% —
  เหตุการณ์แบบนี้พยากรณ์ไม่ได้ แต่ band ที่ดีต้องกว้างพอครอบคลุม

### 2.5 OD ที่ปรับด้วย count (ODME) → พยากรณ์อนาคตด้วย pivot-point

เมื่อโมเดลฐานยังเทียบ count ได้ไม่ดีพอ (สถานะปัจจุบันของโปรเจกต์นี้: GEH<5 = 3.9%
ดู `docs/CALIBRATION.md`) วิธีที่งานที่ปรึกษาใช้กันคือ **ODME** (OD matrix estimation)
คือดัดเมทริกซ์ OD ให้ปริมาณบน link เข้าใกล้ค่าที่นับได้จริง คำถามที่ต้องตอบก่อนทำคือ
"แล้วเมทริกซ์ที่ถูกดัดแล้ว เอาไปพยากรณ์อนาคตอย่างไร"

**หลักที่ต้องเข้าใจก่อน: ODME ให้ "OD ปีฐาน" ไม่ได้ให้ "พฤติกรรม"**
เมทริกซ์หลัง ODME คือภาพถ่ายปีฐานที่ถูกบังคับให้ตรงกับ count มันไม่รู้ว่าทำไมคนถึงเดินทาง
จึงเติบโตเองไม่ได้ ห้ามคูณ growth factor ใส่มันตรง ๆ แล้วเรียกว่าการพยากรณ์

**วิธีที่ถูก: pivot-point (incremental forecasting)** — ใช้ *ระดับ* จากข้อมูลจริง
และใช้ *อัตราการเปลี่ยนแปลง* จากโมเดลพฤติกรรม

```
OD_อนาคต(i,j) = OD_ODME_ฐาน(i,j) × [ OD_โมเดล_อนาคต(i,j) / OD_โมเดล_ฐาน(i,j) ]
```

ขั้นตอนจริง:

1. ปรับเทียบโมเดล 4-step ให้ดีที่สุดเท่าที่โครงสร้างจะทำได้ (§1) — **ยังไม่แตะ ODME**
2. ทำ ODME กับ **ปีฐานเท่านั้น** โดยใช้ OD จาก gravity เป็น seed/prior
3. รัน 4-step ซ้ำด้วย socioeconomic ปีอนาคต (§2.1) ได้ `OD_โมเดล_อนาคต`
   — ใช้ **โมเดลตัวเดียวกัน สมมติฐานเดียวกัน** กับที่สร้าง `OD_โมเดล_ฐาน`
4. คำนวณอัตราส่วนรายคู่ OD แล้วคูณเข้ากับเมทริกซ์ ODME
5. assign เมทริกซ์ปีอนาคตลงโครงข่ายปีอนาคต (§3)

**กติกาที่ห้ามละเมิด**

| ข้อ | เหตุผล |
|---|---|
| pivot ที่ระดับ **OD** เท่านั้น ห้าม pivot ที่ระดับ link | link ที่เพิ่งตัดใหม่ไม่มีค่าปีฐาน ถ้า pivot บน link โครงการใหม่จะได้ปริมาณ 0 ตลอดกาล |
| จำกัดขนาดที่ ODME ดัดได้ (เช่น ±30–50% ต่อคู่ OD และคุม trip-end รวมรายโซน) | ถ้าปล่อยอิสระ ODME จะลาก OD หนีโครงสร้าง gravity แล้ว pivot จะขยายความบิดเบี้ยวนั้นไปตลอด 30 ปี |
| กัน count ไว้ **15–20% เป็น holdout** ไม่ให้ ODME เห็น | ODME ที่ fit ทุกสถานีย่อมดูดีเสมอ ค่าที่รายงานต้องมาจากสถานีที่ไม่ได้ใช้ fit |
| ถ้าอัตราส่วนคู่ไหน `OD_ฐาน` ใกล้ 0 ให้ fallback เป็น absolute increment | หารด้วยค่าใกล้ศูนย์ทำให้อัตราส่วนระเบิด (คู่ OD ใหม่ที่เพิ่งเกิดจากพื้นที่พัฒนาใหม่) |
| รายงานทั้งผลก่อนและหลัง ODME | ผู้ตรวจต้องเห็นว่าส่วนไหนมาจากโมเดล ส่วนไหนมาจากการดัดเข้าหา count |

**ข้อจำกัดที่ต้องเขียนในรายงาน**

- ODME แก้ปีฐานได้ แต่ไม่ได้ทำให้ **scenario** แม่นขึ้น เมทริกซ์ที่ fit กับโครงข่ายเดิม
  ไม่จำเป็นต้องสมเหตุผลเมื่อโครงข่ายเปลี่ยน (มอเตอร์เวย์สายใหม่ ค่าผ่านทางใหม่)
- ยิ่ง ODME ต้องดัดมาก ผลพยากรณ์ยิ่งอ่อนไหวต่อ ODME มากกว่าต่อสมมติฐานอนาคต
  ซึ่งกลับหัวกลับหางกับสิ่งที่การศึกษาต้องการตอบ — ถ้าต้องดัดเกินครึ่ง แปลว่าโครงสร้าง
  แบบจำลอง (โซน โครงข่าย การกระจาย) ยังผิดอยู่ ต้องกลับไปแก้ที่ต้นทางก่อน
- ODME **ไม่ใช่ทางลัดข้าม §1** — เกณฑ์ validation ปีฐานยังต้องผ่านด้วยตัวโมเดลเองในระดับหนึ่ง
  ก่อนจะให้ ODME เก็บส่วนที่เหลือ

**เครื่องมือ**: ODME เต็มรูปแบบ (PTV Visum – TFlowFuzzy) อยู่นอกไปป์ไลน์นี้ ดู §5
ในโปรเจกต์นี้ทำได้ระดับ ODME อย่างง่าย: ปรับตัวคูณรายโซน/รายกลุ่มเส้นทางด้วย least squares
เทียบ `model/5_calibration/scatter_final.csv` โดยยึด OD จาก gravity เป็น prior

## 3. การ code โครงการพัฒนา / ขยายถนน / เชื่อมโครงข่าย (scenario testing)

### 3.1 โครงสร้าง scenario มาตรฐาน
ทุกปี horizon ต้องมีอย่างน้อย 3 เครือข่าย เปรียบเทียบกันเป็นคู่:

| Scenario | โครงข่าย | ใช้ตอบ |
|---|---|---|
| **Do-nothing (Base)** | ปีฐาน ไม่เพิ่มอะไร | สภาพปัญหาถ้าไม่ทำอะไร (V/C อนาคต) |
| **Do-minimum (Committed)** | + โครงการที่ผูกพันงบ/กำลังก่อสร้างแล้วเท่านั้น | ฐานเปรียบเทียบที่ถูกต้องของโครงการใหม่ |
| **Do-something (Build)** | Committed + โครงการที่ศึกษา | ผลของโครงการ = Build − Committed |

⚠️ จุดผิดบ่อย: เทียบ Build กับ Base (ไม่ใส่ committed) → ประโยชน์โครงการเกินจริง เพราะนับผลของ
โครงการอื่นที่ยังไงก็จะเกิดรวมเข้ามาด้วย

### 3.2 การ code โครงข่าย
- **ขยายถนน (เพิ่มเลน):** แก้ attribute ของ link เดิม — `lanes` → ความจุใหม่ตาม HCM/คู่มือ ทล.
  (ต่อเลนต่อทิศ: มอเตอร์เวย์ ~2,000–2,200 pcu/ชม, ทางหลวงหลายเลน ~1,800–2,000, 2 เลนสวนกัน
  ~1,400–1,700 รวมสองทิศ ปรับตามภูมิประเทศ/ไหล่ทาง) + ความเร็ว free-flow ใหม่ ; ฟังก์ชัน BPR เดิม
  (`t = t0·(1+0.15·(v/c)^4)`) ใช้ต่อได้
- **เส้นทางใหม่ / เชื่อมโครงข่าย:** เพิ่ม link+node ใหม่ — **topology ต้องต่อกันจริง**: node ปลายเส้นใหม่
  ต้อง snap ตรง node โครงข่ายเดิม (บทเรียนโปรเจกต์นี้: กราฟที่ไม่ node ที่จุดตัด T-junction เคยแตกเป็น
  24,642 ชิ้น — ดู [CALIBRATION.md](CALIBRATION.md)) ; ทางด่วน/มอเตอร์เวย์เข้าออกได้เฉพาะ ramp
  ต้อง code ramp เป็น link จริง ไม่ใช่ปล่อยให้เชื่อมทุกจุดตัด
- **ค่าผ่านทาง:** เพิ่มเป็น generalized cost (นาที + ค่าผ่านทาง/VOT) ใน cost function ของ assignment —
  ปัจจุบันโมเดลใช้เวลาอย่างเดียว ถ้าทดสอบมอเตอร์เวย์เก็บเงินต้องเพิ่มมิตินี้ก่อน ไม่งั้นปริมาณเกินจริง
- **ปีเปิดใช้:** ผูกโครงการกับปี horizon (§2.2) — โครงการหนึ่งอาจอยู่ใน 2589 แต่ไม่อยู่ใน 2579

### 3.3 การวิเคราะห์ผลโครงการ
- **Select link analysis** — ดูว่า traffic บนเส้นใหม่มาจาก OD ไหน (ใน pipeline ปัจจุบันทำได้จาก
  dijkstra `return_predecessors` ที่มีอยู่ใน `scripts/lib/passign.py` แล้ว; ใน Visum เป็นเครื่องมือสำเร็จ)
- **Diff map**: flow(Build) − flow(Committed) รายเส้น → เห็นการดึง traffic จากถนนขนาน
  (นี่คือการตรวจ "ถนนความจุมากแต่ปริมาณน้อย" อย่างเป็นระบบ — ถ้าเส้นใหม่ยังดึงไม่ได้ = ปัญหา
  connector/โซนแบบที่พบกับทางด่วนใน [LIMITATIONS.md](LIMITATIONS.md) §4)
- **ตัวชี้วัดโครงข่าย** (รวมทั้งระบบ, Build vs Committed): VKT, VHT, ความเร็วเฉลี่ยถ่วง flow,
  V/C distribution, เวลาประหยัด (→ เข้า EIRR/NPV ตามแนว สศช.)
- **ตัวชี้วัดการเชื่อมโยง (connectivity/accessibility):** เวลาเข้าถึงถ่วงประชากร (เช่น ประชากรที่ถึง
  รพ.ศูนย์/สนามบิน/ท่าเรือใน 60/90/120 นาที ก่อน-หลัง), logsum จากขั้น mode choice
  (มี logit อยู่แล้ว → Δlogsum = ผลประโยชน์ผู้เดินทางแบบรวมทุกโหมด ถูกหลักกว่าเวลาอย่างเดียว)

## 4. โมเดลระดับประเทศ → โมเดลพื้นที่ศึกษา (subarea extraction / windowing)

หลักการ: โมเดลประเทศ **ไม่ละเอียดพอ** สำหรับโครงการเฉพาะจุด (เห็นแล้วจากทางด่วน flow=0)
แต่**สิ่งที่มันให้ได้ดีคือ demand จากภายนอกพื้นที่** — จึงตัดหน้าต่าง (window) แล้วทำละเอียดข้างใน

### 4.1 กำหนดขอบเขต (cordon) ตามขนาด/ประเภทโครงการ
ขอบเขตต้องครอบ **influence area** ของโครงการ — เส้นทางเลือก (alternative routes) ทั้งหมด
ต้องอยู่ในหรือถูกแทนด้วย external station:

| ประเภทโครงการ | ขนาดพื้นที่ศึกษาแนะนำ | โซนภายใน |
|---|---|---|
| ปรับปรุงทางแยก/ถนนในเมือง | เทศบาล/อำเภอเดียว + กันชน | ตำบล หรือละเอียดกว่า (แบ่งเอง) |
| บายพาส/ถนนเลี่ยงเมือง | ทั้งจังหวัด | ตำบล |
| มอเตอร์เวย์/ทางหลวงระหว่างเมือง | กลุ่มจังหวัดตามแนวเส้น + จังหวัดที่มีเส้นขนาน | ตำบลใกล้แนว, อำเภอไกลแนว |
| ท่าเรือ/นิคม/สนามบิน | จังหวัด + โครงข่าย hinterland หลัก | ตำบล + โซนพิเศษ (gate เป็นโซนเอง) |

ข้อมูลพร้อมแล้ว: GADM ADM_3 = **5,926 ตำบล** อยู่ใน `data/boundaries/gadm41_THA.gpkg`
และ pipeline สร้าง centroid ถ่วงประชากร + connector มีอยู่ (ใช้ซ้ำกับตำบลได้)

### 4.2 โครงสร้างโซนของโมเดลพื้นที่
- **ภายใน cordon:** ตำบล (หรือละเอียดกว่าใกล้โครงการ)
- **นอก cordon:** ไม่ต้องมีโซนจริง — แทนด้วย **external stations** = จุดที่ถนนสายหลักตัด cordon
  (สถานีละ 1 โซน) ปริมาณเข้า-ออกแต่ละสถานีเอามาจากโมเดลประเทศ + นับจริงถ้ามี
- OD ของโมเดลพื้นที่จึงมี 4 ส่วน: **I–I** (ภายใน, สร้างใหม่จาก trip gen ตำบล) ·
  **I–E / E–I** (ปลายในปลายนอก) · **E–E (through)** — สองส่วนหลังดึงจากโมเดลประเทศ

### 4.3 ดึง demand ภายนอกจากโมเดลประเทศ
วิธีตามหลัก (ทำได้ทั้งใน pipeline ปัจจุบันและ Visum):
1. Assign โมเดลประเทศปี horizon ที่ต้องการ (per-component ก็ได้ — โครงสร้าง 7 องค์ประกอบ
   ที่ additivity ตรวจแล้วช่วยแยกคน/สินค้าให้ external station อัตโนมัติ)
2. ระหว่าง trace path (มี predecessors จาก dijkstra อยู่แล้ว) ตรวจว่า path ตัด cordon ที่ link ไหน →
   บันทึก (O, D, จุดตัดเข้า, จุดตัดออก, ปริมาณ)
3. รวมเป็น OD ใหม่: O/D ที่อยู่นอก cordon ถูกแทนด้วย external station ที่ path นั้นใช้ →
   ได้ E–E matrix (through) + I–E/E–I matrix พร้อมใช้
4. ใน **Visum**: ขั้นตอนนี้คือเครื่องมือสำเร็จรูป **Subnetwork Generator** — import โมเดลประเทศเข้า
   Visum ก่อน (ตาราง §5.2) แล้วตัด subarea ได้เลย พร้อม cordon matrices
- through/external trips ของปีอนาคต → ใช้โมเดลประเทศปี horizon นั้น (ไม่ใช่ factor จากปีฐานเฉย ๆ)

### 4.4 ทำละเอียดภายใน + calibrate ใหม่ (บังคับ)
- **โครงข่าย:** เพิ่มถนนรอง/ถนน อปท. ใน OSM ที่โมเดลประเทศกรองทิ้ง + ramp/connector เข้าทางพิเศษ
  (แก้ปัญหา LIMITATIONS §4 ทางด่วน flow=0 โดยตรง ถ้าพื้นที่ = กทม.-ปริมณฑล)
- **Trip gen ภายใน:** ประชากร WorldPop รายตำบล (zonal stats — pipeline มีอยู่) + landuse จริง
  ในพื้นที่ (สำรวจ/ข้อมูลท้องถิ่น ดีกว่า proxy ระดับประเทศ)
- **Calibrate ในพื้นที่ — ห้ามข้าม:** นับจราจรท้องถิ่น (moving car / ATC / ข้อมูล AADT สถานีในพื้นที่ +
  นับเสริมจุดสำคัญ) → ปรับ trip rate, distribution, assignment จนผ่านเกณฑ์ §1 *ภายในพื้นที่ศึกษา*
  — เกณฑ์ GEH ที่โมเดลประเทศไม่ผ่าน ต้องผ่านให้ได้ในสเกลนี้ เพราะข้อมูลละเอียดพอแล้ว
- ถ้ามี count มากพอ ใช้ **ODME** (OD matrix estimation จาก count — มีใน Visum: TFlowFuzzy)
  ปรับ OD ขั้นสุดท้าย โดยยึด OD จากโมเดลเป็น seed/prior เสมอ (อย่าให้ ODME ลาก OD หนีโครงสร้างเดิมไกล)

### 4.5 การตรวจความสอดคล้อง (consistency checks)
- ผลรวมเข้า-ออกทุก external station ของโมเดลพื้นที่ = โมเดลประเทศ (± ที่ปรับกับ count จริง)
- ตรวจ through-traffic บนเส้นหลัก: โมเดลพื้นที่ไม่ควรเบี่ยง through ออกนอก cordon
  (ถ้าเกิด แปลว่า cordon เล็กไป — ขยาย)
- Screenline ภายในอย่างน้อย 2–3 แนว ตัดแนวการเดินทางหลัก

## 5. การส่งต่อเครื่องมือเฉพาะทาง (PTV Visum + Excel + R + QGIS)

### 5.1 แบ่งบทบาทตามจุดแข็ง
| เครื่องมือ | บทบาทที่เหมาะ |
|---|---|
| **PTV Visum** | network + scenario management (versioning ในตัว), equilibrium/stochastic assignment ที่ผ่านการพิสูจน์, **Subnetwork Generator** (§4.3), select link, ODME (TFlowFuzzy), matrix ops |
| **R (RStudio)** | regression trip rate ~ socioeconomics, ประมาณ elasticity จากอนุกรม AADT/GDP, ตรวจ calibration (GEH/R² อัตโนมัติ), การ interpolate รายปี §2.2, กราฟรายงาน |
| **Excel** | growth factor sheet, ตารางสมมุติฐานสูง/กลาง/ต่ำ, สรุปเศรษฐศาสตร์โครงการ (EIRR/NPV), ตารางส่งรายงาน |
| **QGIS (pipeline นี้)** | เตรียมข้อมูลเชิงพื้นที่ (โซน/centroid/zonal stats), ตรวจ topology, แผนที่ผลลัพธ์/diff map, และยังรันโมเดลระดับประเทศต่อได้ตาม pipeline เดิม |

### 5.2 ข้อมูลที่มีอยู่ → นำเข้า Visum
| ข้อมูลปัจจุบัน | ไฟล์ | นำเข้า Visum เป็น |
|---|---|---|
| โครงข่ายถนน (directed, capacity, speed) | `model/4_trip_assignment/assigned_final_dist.gpkg` | Links/Nodes (import Shapefile/GeoPackage → กำหนด TypeNo จาก highway class) |
| โครงข่ายราง/อากาศ/น้ำ + terminals | `data/network/`, `data/multimodal/` | PuT network / เชื่อมเป็นระบบขนส่งแยก TSys |
| TAZ อำเภอ + centroid + connectors | `data/zones_taz/` | Zones + Connectors |
| OD matrices (คน/สินค้า รายโหมด) | `model/2_distribution/`, `model/3_mode_choice/` | Matrices (CSV → Visum matrix; ระวังลำดับโซนต้องตรง zone no.) |
| สถานี AADT + ค่าเป้า 2569 | `data/calibration/aadt_current.csv` + geolocated gpkg | Count locations (สำหรับ calibrate/ODME) |
| พารามิเตอร์ (BPR α=0.15 β=4, K-factor, logit β/ASC) | `config/model_params.py`, `config/calibrated_params.py` | Volume-delay function + mode choice params |

### 5.3 ข้อควรระวังตอนย้ายเครื่องมือ
- **ผลจะไม่เท่าเดิม** — Visum ใช้ equilibrium (LUCE/Bi-conjugate FW) ต่างจาก multi-path MSA
  ของ pipeline นี้ → ต้อง re-validate กับ AADT ใน Visum ใหม่ ห้ามยกตัวเลข calibration เดิมไปอ้าง
- Zone numbering / ทิศทาง link (oneway) / หน่วย (PCU-ชม.peak vs คัน-วัน) ต้อง map ให้ชัด —
  โมเดลนี้ assign เป็น peak-hour PCU แล้วหารกลับเป็นวัน (K-factor) ต้องเลือกใน Visum ให้ตรงกัน
- เอกสารที่ต้องพกไปด้วยเวลาย้าย: [METHODOLOGY.md](METHODOLOGY.md) (สมการทุกขั้น),
  [MODEL_INPUTS.md](MODEL_INPUTS.md), [LIMITATIONS.md](LIMITATIONS.md) — ข้อจำกัดข้อมูล
  ไม่หายไปเพราะเปลี่ยนซอฟต์แวร์

## ลำดับการพัฒนา (แนะนำ)
1. เลือกพื้นที่ศึกษา/โครงการนำร่อง → กำหนด cordon (§4.1)
2. หา socioeconomic ปีอนาคต + committed projects (§2.1) — งานข้อมูล เริ่มได้ทันที
3. ยกระดับโมเดลประเทศตาม LIMITATIONS §6 ข้อ 1 (พิกัด AADT) — เพดานหลักของทุกอย่าง

5. ค่อยทำ scenario ปีอนาคต (§2–3) บนโมเดลพื้นที่ที่ผ่านเกณฑ์แล้ว
